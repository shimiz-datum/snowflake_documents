# [Snowpipe](https://docs.snowflake.com/en/user-guide/data-load-snowpipe-intro)

# 1. ドキュメント概要（初学者向け）

このドキュメントは、Snowflake の **Snowpipe（スノーパイプ）** を使って、クラウドストレージ上のファイルを **継続的（連続的）にテーブルへロードする仕組み** を説明しています。

Snowpipe を使うと、従来のように `COPY INTO` をスケジュール実行して「まとまったバッチ」で取り込むのではなく、**ファイルがステージに到着したら数分以内にマイクロバッチとして取り込む** ことができます。

## Snowflake全体の中での位置づけ
Snowflake にデータを取り込む方法は大きく分けて次の 2 つがあります。

- **一括ロード（Bulk load）**：`COPY INTO` を実行してまとめて取り込む
- **連続ロード（Continuous load）**：Snowpipe を使い、ファイル到着に合わせて継続的に取り込む

このページは、そのうち **Snowpipe（連続ロード）** の概要・動作・違い・注意点などを公式仕様に沿って説明しています。

【補足】  
ここでいう **ステージ（stage）** は、クラウドストレージや Snowflake 管理領域にある「ロード元ファイルを置く場所」です。Snowpipe はこのステージ上の新規ファイルを検知してロードします。

## Snowpipeの仕組み
Snowpipe は、ファイルがステージで利用可能になり次第、ファイルからデータをロードします。  
データは、参照パイプで定義されている **<span style="color:red"> `COPY` ステートメントに従ってロード</span>** されます。

- **パイプ（pipe）** は、Snowpipe で使用される `COPY` ステートメントを含む、名前付きの **ファーストクラス Snowflake オブジェクト** です。
- `COPY` ステートメントは次を識別します：
  - データファイルのソースの場所（= ステージ）
  - ロード先のターゲットテーブル
- JSON や Avro などの **半構造化データ型を含む、すべてのデータ型がサポート** されています。
- ステージングされたファイルを検出するための **さまざまなメカニズム** が利用可能です。

【補足】  
**パイプ（pipe）** は「Snowpipe がどうやってどこからどのテーブルへロードするか」を保持する設定オブジェクトです。中身は `COPY` 文（ロード定義）です。

---

### クラウドメッセージングを使用したSnowpipeの自動化（自動データロード）
自動データロードは、クラウドストレージの **イベント通知** を活用して、ロードする新しいデータファイルの到着を Snowpipe に通知します。

- Snowpipe はイベント通知を **キューからポーリング** します。
- キュー内のメタデータを使用して、Snowpipe は次を行います：
  - 指定されたパイプオブジェクトで定義されたパラメーターに基づき
  - 新しいデータファイルをターゲットテーブルに
  - **サーバーレスで継続的にロード** します

【補足】  
「イベント通知＋キュー」という仕組みで、新しいファイル到着が Snowpipe に伝わり、自動でロードが進むイメージです。

---

### Snowpipe REST エンドポイントの呼び出し
クライアントアプリケーションは、次を指定して **パブリック REST エンドポイント** を呼び出します：

- パイプオブジェクトの名前
- データファイル名のリスト

そして、リストに一致する新しいデータファイルが、パイプオブジェクトで参照されたステージで検出された場合、それらは **ロードのためにキューに入れられます。**

Snowflake が提供するコンピューティングリソースは、パイプで定義されたパラメーターに基づいて、キューから Snowflake テーブルにデータをロードします。

【補足】  
この方式は「クラウドイベント通知で自動検知」ではなく、「REST API でロード対象を知らせる」ことでロードを進める形です。

### 重要（イベントフィルタリング推奨）
Snowflake は、Snowpipe 用の **クラウドイベントフィルタリング** を有効にして、次を削減することを推奨しています：

- コスト
- イベントノイズ
- 遅延

【補足】

## Snowpipeと一括データロードとの相違点
このセクションでは、Snowpipe と、`COPY` コマンドを使用した **一括データロード** ワークフローの主な違いを簡単に説明します。  
Snowpipe のドキュメント全体に追加の詳細が記載されています。

---

## 認証（Authentication）
- **一括データロード（Bulk load）**  
  ユーザーセッションを認証および開始するために、クライアントがサポートするセキュリティオプションに依存します。

- **Snowpipe**  
  REST エンドポイントを呼び出すとき：
  - **キーペア認証** と **JSON Web トークン（JWT）** が必要です。
  - JWT は、RSA 暗号化を使用した **公開/秘密鍵ペア** で署名されます。

【補足】  
ここでの認証差は「人がログインして SQL を打つ」形と「API を呼び出す」形の違いに対応しています。

---

## ロード履歴（Load history）
- **一括データロード（Bulk load）**
  - ターゲットテーブルのメタデータに **64 日間** 保存されます。
  - `COPY` ステートメント完了時に、ステートメントの出力として利用可能です。

- **Snowpipe**
  - パイプのメタデータに **14 日間** 保存されます。
  - REST エンドポイント、SQL テーブル関数、または `ACCOUNT_USAGE` ビューを介して Snowflake からリクエストする必要があります。

### 重要（ファイルの再ロード回避）
ファイルの再ロード（およびデータの重複）を回避するには、  
**一括データロードまたは Snowpipe のいずれか一方** を使用して特定のファイルセットからデータをロードすることを推奨します。

【補足】  
同じファイルを別方式でもロードすると重複が起き得るため、「どちらかに統一する」意図です。

---

## トランザクション（Transactions）
- **一括データロード（Bulk load）**
  - ロードは常に **単一のトランザクション** で実行されます。
  - データは、ユーザーが手動で送信した他の SQL ステートメントと共にテーブルに挿入されます。

- **Snowpipe**
  - ロードは、各データファイルの行の数とサイズに基づいて、**単一のトランザクションに結合** または **複数のトランザクションに分割** されます。
  - 部分的にロードされたファイルの行（`ON_ERROR` コピーオプション設定に基づく）も、1つ以上のトランザクションに結合または分割できます。

【補足】  
Snowpipe はファイルの条件（行数・サイズなど）に応じて、内部的にトランザクションの扱い方が変わる可能性がある、という説明です。

---

## コンピューティングリソース（Computing resources）
- **一括データロード（Bulk load）**
  - `COPY` ステートメントの実行には、ユーザー指定の **ウェアハウス** が必要です。

- **Snowpipe**
  - Snowflake が提供する **コンピューティングリソース** を使用します。

【補足】  
Snowpipe は「ユーザーが起動したウェアハウス」ではなく、Snowflake 側が提供する計算リソースでロードします。

---

## コスト（Cost）
- **一括データロード（Bulk load）**
  - 各仮想ウェアハウスがアクティブである時間に対して請求されます。

- **Snowpipe**
  - ファイルのロード中に **Snowpipe ウェアハウスで使用されるコンピューティングリソース** に応じて請求されます。

---

## 推奨ロードファイルサイズ（Recommended load file size）
Snowpipe で最も効率的で費用対効果の高いロード体験を得るために、次を推奨しています：

- 「ファイルサイズのベストプラクティス」で推奨されるファイルサイズに従う
- **1 分ごとにファイルをステージング** する

【補足】  
「小さすぎる・大きすぎる」ファイルは効率が落ちる可能性があるため、公式の推奨サイズに寄せる意図です。

# 3. 注意点・制約（明記がある場合）

このドキュメント上で明記されている注意点・制約は次のとおりです。

- クラウドプロバイダーの **政府リージョン** では、他の商用リージョンとの間で **イベント通知の送受信は許可されていない**。
- **重要**：Snowpipe 用の **クラウドイベントフィルタリングを有効にすることが推奨**（コスト・イベントノイズ・遅延の削減）。
- **重要**：ファイル再ロード（データ重複）を避けるため、特定のファイルセットのロードは **一括ロードか Snowpipe のどちらか一方に統一する** ことが推奨。
- Snowpipe のロード履歴は **パイプのメタデータに 14 日間** 保存され、REST / SQL テーブル関数 / `ACCOUNT_USAGE` ビュー経由で取得する必要がある（Bulk load は 64 日）。
- Snowpipe の認証（REST エンドポイント呼び出し）には **キーペア認証 + JWT（RSA 署名）** が必要。
- Snowpipe のトランザクションは、データファイルの行数/サイズ等に応じて **結合または分割** され得る。
- Snowpipe は Snowflake 提供のコンピューティングリソースを使用し、コストは Snowpipe ウェアハウスで使用されるリソースに応じて決まる。
- 推奨ロードファイルサイズに従い、**1分ごとのステージング** が推奨される。
